# ADR-011 — Philips Hue Entertainment integration

- **Status:** **Proposed** — implemented this session, not yet validated against the operator's physical bridge/lights
- **Date:** 2026-09-08
- **Relates to:** the operator's own numbered Hue integration spec (13 sections, given in full in the session transcript), ADR-004 (WLED realtime protocol strategy — this integration follows the same evidence-over-assumption discipline), ADR-008 (companion worker vs in-process — the same "no bundled binary, no separate daemon" reasoning extends here)

## Context

The operator wants Hue lights to join WLED as a second, independent realtime Ambilight output, following the same picture on the same bound television, without touching the existing WLED path in any way. Their spec is unusually detailed and already answers almost every design question; this ADR records the concrete decisions made where it left room for engineering judgement, and — per their own explicit instruction not to guess — every place a fact could not be independently verified this session.

## Decision 1 — Transport: adopt `HueApi.Entertainment`, write no DTLS code

**Adopted `HueApi` + `HueApi.Entertainment`, pinned to `3.3.0` (MIT, `michielpost/Q42.HueApi`), rather than a hand-rolled DTLS-PSK client.**

Verified directly from the package's own source at that tag (not assumed from the operator's earlier research, which named an older commit before the project renamed from `Q42.HueApi.Entertainment` to `HueApi.Entertainment`):

- `HueApi.Entertainment.csproj` at `v3.3.0` targets `net8.0;net9.0;net10.0` — directly compatible with this plugin's `net9.0` TFM. (`3.0.0`/`3.1.0` on NuGet targeted only `net8.0`; the newest published version at query time, `3.3.0` from 2026-07-06, is the one actually multi-targeting `net9.0`, confirmed by fetching its `.csproj`, not inferred from the NuGet registration API's dependency-group listing, which only showed one group per version and would have been misleading on its own.)
- `Connection/DtlsClient.cs` and `Connection/UdpTransport.cs` confirm the exact wire parameters the operator's own research named: DTLS 1.2 (`MinimumVersion`/`ClientVersion` = `ProtocolVersion.DTLSv12`), cipher suite restricted to `TLS_PSK_WITH_AES_128_GCM_SHA256`, the application key as the PSK identity and the hex-decoded client key as the PSK (`BasicTlsPskIdentity(_appKey, psk)`), over UDP port 2100 — via `Org.BouncyCastle.Crypto.Tls`, i.e. this plugin implements none of that itself, satisfying the operator's explicit "no home-grown crypto/DTLS" requirement.
- Dependency: `Portable.BouncyCastle` 1.9.0 (MIT). No GPL/AGPL conflict with this project's own GPL-3.0 licensing.

### What "MultiChannelEffect not supported" actually means

The operator flagged this exact documentation phrase as worth checking rather than trusting. Read directly: `StreamingGroup(List<EntertainmentChannel> channels)` builds one `StreamingChannel` per real `channel_id`, and `StreamingGroup.GetCurrentStateAsByteArray` writes one `[channel id][R R G G B B]` block per channel into the HueStream payload — every channel, including multiple channels belonging to one Gradient light, is addressed and coloured independently. The "not supported" note refers to the library's own higher-level scripted-*effects* API (`EntertainmentGroupExtensions.IteratorEffect` and friends, meant for programmatic light shows), not to per-channel colour addressing, which this integration needs and which works. This project does not use that effects layer at all (see Decision 2).

### Two concrete, verified limitations — accepted, not silently absorbed

**1. The DTLS handshake itself cannot be cancelled.** `StreamingHueClient.ConnectAsync` bounds only the initial UDP socket connect with a 5 s `CancellationToken`; the actual handshake — `DtlsClientProtocol.Connect(dtlsClient, _udp)`, from BouncyCastle — is synchronous and blocking, with `UdpTransport.Receive`'s own internal wait/retransmission logic (`SpinWait.SpinUntil`, a `TimeoutException` only at a hardcoded 60 s wait) as the only thing that ever unblocks it. This is exactly the risk the operator's own brief named ("a timeout on opening a UDP socket is not a full handshake timeout"), now confirmed from source rather than assumed. **Mitigation:** `HueDtlsChannel.TryConnectAsync` (`src/Jellyfin.Plugin.RealtimeAmbilight/Hue/HueDtlsChannel.cs`) runs the blocking connect on its own dedicated (`TaskCreationOptions.LongRunning`) thread, races it against this plugin's own timeout, and on timeout closes the underlying socket to force the blocked handshake thread to unwind rather than leaving it stuck — an *abandon*, not a true cancel, since the library gives no true cancel. Documented as a known limitation, not a solved problem: a genuinely wedged handshake still occupies a background thread until the socket close actually unblocks it, which was not measured against real hardware this session.

**2. `StreamingHueClient`'s own REST call inside `ConnectAsync` (`LocalHueApi.SetStreamingAsync`, which `PUT`s `entertainment_configuration/{id}` with `{"action":"start"}`) uses `HttpClientHandler.DangerousAcceptAnyServerCertificateValidator`** — confirmed by reading `LocalHueApi.cs`'s private `GetConfiguredHttpClient`, which falls back to that exact callback whenever no `HttpClient` is passed in, and `StreamingHueClient`'s constructor never passes one. This is precisely the "don't copy an accept-any callback" anti-pattern the operator's brief warned against, and there is no public API to override it on `StreamingHueClient` — its `LocalHueApi` field is private, and `StreamingHueClient` has no constructor overload accepting a custom `HttpClient`. **Mitigation, and its real scope:** every REST call this plugin makes on its own behalf — discovery, pairing (the most credential-sensitive moment), reading entertainment configurations, and the end-of-session light PUTs — goes through `HueBridgeClient`/`HueLightControl`, which build their own `HttpClient` with a certificate-pinning `ServerCertificateCustomValidationCallback` (Decision 4), never the library's default. The one call still using the dangerous default is `SetStreamingAsync` inside `ConnectAsync`, reachable only after pairing has already succeeded via this plugin's own pinned client, and only over the local LAN to an address the operator explicitly selected. This narrows, but does not eliminate, the exposure; it is recorded here so it is not silently forgotten. **Not fixed this round**; a future round could reimplement the ~15-line `ConnectAsync` body directly against this plugin's own pinned `LocalHueApi` instance plus the library's (internal, so not directly reusable without a small copy) DTLS classes, trading a bit of duplication for closing this gap entirely.

### Packet framing: written independently, not taken on trust

Rather than depend on `StreamingGroup`'s own effects/dirty-tracking state machine for something as simple as "send this frame's colours" (see Decision 2 for why), this plugin has its own `HueStreamPacketizer` (`Core/Hue/Protocol/HueStreamPacketizer.cs`). Its exact byte layout — `"HueStream"` (9 ASCII bytes), version `0x02 0x00`, a 1-byte sequence number, 2 reserved bytes, 1 colour-space byte (`0x00` = RGB), 1 more reserved byte, the entertainment configuration id as 36 lowercase hyphenated ASCII bytes (`Guid.ToString("D")`), then per channel `[1-byte channel id][R,R,G,G,B,B]` (an 8-bit value duplicated into both bytes of each nominally-16-bit field, not true 16-bit precision) — was read directly from `HueApi.Entertainment`'s own `StreamingGroup.GetCurrentStateAsByteArray`/`StreamingState.ToByteArray` at the pinned tag, since the primary Hue reference (`developers.meethue.com`'s API docs) sits behind a developer-portal login this environment cannot reach. `HueStreamPacketizerTests` checks every field position, the real (non-sequential-safe, per-channel) id encoding, the duplicated-byte colour encoding, and the 20-channels-per-message chunking boundary against values computed independently of the packetizer itself, not by round-tripping encode→decode against itself.

## Decision 2 — Shared analysis, independent distribution

**One FFmpeg decode, one `PlaybackEventCoordinator`; two independent one-slot subscriptions to its frames.**

`LatestFrameBuffer<TFrame>.TryTake` atomically empties the buffer for whichever caller reads it first (`Interlocked.Exchange(ref _latest, null)`), which is exactly right for one consumer and exactly wrong for two: WLED's existing `LatestFrameOutputScheduler` and a new Hue path calling `TryTake` on the same buffer would race and steal frames from each other. `Core/Playback/FanOutFrameBuffer.cs` (new) sits where `PlaybackEventCoordinator.LatestFrames` used to be a plain `LatestFrameBuffer<AnalysisFrame>`: the analysis worker still calls one `Publish`, which now fans the same immutable `AnalysisFrame` instance out to every subscriber's own independent `LatestFrameBuffer<AnalysisFrame>` (obtained via `Subscribe()`). `JellyfinWledOutputService` now calls `_coordinator.LatestFrames.Subscribe()` instead of holding the coordinator's buffer directly; `HueEntertainmentService` does the same for its own. Each output's buffer is bounded (one slot) and independently drained; a slow or entirely absent Hue consumer only ever replaces its own stale frame and can never block or steal WLED's.

**Hue's own colour path runs entirely upstream of WLED's.** `HueFrameProcessor` (`Core/Hue/HueFrameProcessor.cs`) samples the same `AnalysisFrame` WLED's `AmbilightFrameProcessor` does, but through its own `EdgeSampler`/`SceneAverageSampler` calls with its own small, fixed logical sampling layout (12/8/12/8 samples per side — independent of any physical WLED LED count, so it stays correct with no WLED strip configured at all) and its own `BlackBorderDetector` instance. None of WLED's gamma encoding, temporal dithering, physical-LED interpolation, wall-colour correction, or per-side RGB trims are anywhere on Hue's path — those are properties of a specific WLED installation, not of the picture, and the operator's spec is explicit that they must not leak into Hue.

Deliberately **not** shared: the black-border detector. `AmbilightFrameProcessor` does not expose its internal one, and refactoring it to share state was judged riskier this round than a second, independent, cheap per-frame scan — the one thing this integration must never do is destabilise already-working WLED behaviour.

## Decision 3 — Spatial mapping

`Core/Hue/Mapping/HueChannelMapper.cs`, pure and unit-tested (`HueChannelMapperTests`). Given a channel's own reported `HuePosition{X,Y,Z}` (from `entertainment_configuration.channels[].position`, per the CLIP v2 schema — field names cross-checked against `aiohue`'s own `entertainment_configuration.py` model, since `developers.meethue.com`'s reference is unreachable this session), three anchors blended smoothly across depth:

| Depth (`Y`, clamped to `[0, 1]`) | Anchor |
|---|---|
| 0 — at the screen | The picture's own top/bottom edge blended by height (`Z`), blending further toward the nearer side edge as `X` approaches ±1 |
| 0.5 — beside the viewer | The corresponding full left/right image edge (by sign of `X`), positioned along it by height |
| 1 — behind the viewer | The whole active picture's average colour (`SceneAverageSampler`, new — averages every pixel inside the crop, not just the edge band, since the operator's spec explicitly rejects an edge-only average as "insufficient" for a scene with a bright centre and dark border) |

Depth blends piecewise-linearly across those three points; within the "at the screen" anchor, height and left/right-extremity blends are themselves smooth (no hard thresholds anywhere in the function). `X`/`Z`-to-edge-run fraction formulas follow `EdgeSampler`'s own documented clockwise sample order for each of its four runs (verified against its source, not assumed) so a channel's mapped point lines up with the same physical direction WLED's own LEDs sample.

**Axis convention — stated, and explicitly unverified this session.** `X`: left (−1) to right (+1) facing the screen. `Y` (depth): 0 at/near the screen, increasing toward and past the viewer. `Z` (height): 0 at the floor, increasing toward the ceiling. This is the convention consistently described across every third-party Hue Entertainment client this project could inspect, but **not confirmed against the primary reference**, which is behind a developer-portal login this environment cannot reach, and **not confirmed against the operator's own bridge** — obtaining real position data requires paired credentials, and pairing requires the physical link button, which this session was explicitly told not to simulate. First item on the hardware checklist below: place one light unambiguously (directly beside the screen, say) and confirm its reported `X` reads near 0 and `Y` reads near 0 before trusting anything the mapping produces.

## Decision 4 — Credential storage and certificate handling

**Server-side only, never a field on `PluginConfiguration`.** That class is exactly what Jellyfin's own `GET /Plugins/{id}/Configuration` returns verbatim to any admin browser session; keeping the application key and client key structurally outside it (`Hue/HueCredentialStore.cs`, its own small file under the plugin's `DataFolderPath`) is what actually keeps them out of a generic configuration response, not a UI choice to merely hide a field that is still there.

**Encrypted at rest with ASP.NET Core's own Data Protection API** — a standalone `DataProtectionProvider` (not the DI-registered one, whose availability from a plugin's own service registration is not guaranteed), with its key ring stored in a sibling directory alongside the encrypted credentials file, both under `DataFolderPath`. **Backup behaviour, stated explicitly per the operator's own requirement:** the key ring and the ciphertext must travel together; a directory-level backup naturally keeps them together, and if only the ciphertext survives (a partial backup, or a restore onto a host whose key ring was never carried over), decryption fails and is treated identically to "never paired" — the operator re-pairs, rather than the plugin crashing or producing garbage credentials.

**Certificate validation: trust-on-first-use pinning by SHA-256 thumbprint, not a public-CA chain check.** A Hue bridge's HTTPS certificate is self-signed and device-specific; there is no CA chain to validate against, and reusing a "trust the OS CA store" callback would either reject every bridge outright or (if relaxed) devolve into exactly the accept-any pattern the operator warned against. Instead: the discovery-time probe (`HueBridgeClient.ProbeAsync`, the one call made before any trust exists at all) accepts whatever certificate answers and records its SHA-256 thumbprint for display; every call made *after* pairing (`CreatePinnedClient`) validates the presented certificate's thumbprint against the one captured and stored at pairing time, refusing and logging a warning on any mismatch. A bridge that moves to a new IP address and is rediscovered there is re-identified by its own `bridgeid` (from `/api/config`) before its thumbprint is trusted for anything beyond re-probing — never by address alone, per the operator's explicit "do not trust keys to another device at that address" requirement.

**Caught and fixed in review, after this session's implementation pass:** `HueController.PairAsync` originally returned the internal `HuePairingResult` record directly, which carries the raw application key and client key up from `HueBridgeClient.TryPairAsync` so they can be handed to `HueCredentialStore.SaveAsync` — but returning that same record from the HTTP endpoint sent both secrets to the browser in the pairing response body, for no functional reason (the settings page only ever reads `Success`/`FailureReason`). This is exactly the exposure this decision's first paragraph says `HueCredentialStore` exists to prevent, just via a different path than a `PluginConfiguration` field. Fixed by returning a new, separate `HuePairingResponse(bool Success, string? FailureReason)` DTO instead, with no route from the internal credential-carrying type to any HTTP response. No other endpoint in `HueController` was found to have the same issue — `GetStatus`/`GetEntertainmentConfigurationsAsync`/`GetBridgesAsync` all return bridge-side or status data, never `HueCredentials` or `HuePairingResult`.

## Decision 5 — Natural-light filter, and the 1% floor

`Core/Hue/HueNaturalLightFilter.cs`, pure, deterministic, driven entirely by an explicit `elapsedMilliseconds` parameter (never a frame count, never the wall clock read internally) — the same testability discipline this project already applies to `DwellFilter`. Brightness (Rec. 709 luma of the mapped colour) and colour (the mapped colour normalized by its own brightness — its hue/chroma direction with brightness factored out) are smoothed independently as two first-order low-passes with different time constants (colour: 500 ms, slower — an abrupt colour swap between differently lit shots is exactly what "suppress abrupt colour changes" asks for; brightness: 180 ms, faster, so the light still reads as reactive), plus a second, independent hard clamp on brightness's own rate of change (2.5 units/second, normalized 0–1) applied *after* smoothing — this is specifically what suppresses a short, sharp peak: a smoothing time constant alone still lets a single-frame jump produce a brief but full-amplitude spike, and the rate clamp bounds how long any change can take regardless of how large the jump was.

**Deliberately not `DwellFilter` or `DitheredRgb24Encoder`, reused or adapted.** Those exist to fix WLED-specific problems — a single-frame flash snapping a physical LED strip, 8-bit quantization banding — that do not apply to a 16-bit Hue light, and reusing them would carry WLED-specific behaviour into a profile the operator explicitly wants kept separate ("Verspreid geen WLED-dithering of WLED-specifieke filters naar Hue").

**The 1% floor is a term in the brightness calculation, not a per-component RGB minimum.** `floored = 0.01 + (dimmed × 0.99)`, where `dimmed` already includes the operator's own overall-brightness control — i.e. the floor is applied *after* that control, so it survives dimming instead of being dimmed away with everything else, per the operator's explicit requirement. **Stated plainly as a software target, not a physical guarantee:** what 1% of the computed brightness actually looks like on the wall depends on the specific light's own minimum dimming level and its relationship between the CLIP v2 `dimming.brightness` percentage, linear luminance, and perceived brightness — none of which this session could measure without live hardware.

**On full black, the filter holds the last colour that was actually on screen (with a warm-white, 2700 K-ish, fallback before any real colour has ever been seen), never snapping to black or an undefined hue** — exactly the operator's "avoid colour flicker around black" requirement, satisfied structurally rather than by a special case: brightness fades toward the floor on its own smoothing/rate-clamp path, while the colour direction the floor's dim light is multiplied by simply stops updating (there is no black hue to update toward) and keeps whatever it last was.

## Decision 6 — Lifecycle state machine

`Core/Hue/HueEntertainmentStateMachine.cs`: `Unpaired → Ready → Connecting → Streaming ⇄ Paused → Stopping → Ready`, with `Recovering` (reached from `Connecting`, `Streaming`, or `Paused` on a transient issue) and `RelinkRequired` (reached from anywhere paired, on a permanent one) as the two failure branches, matching the eight states the operator's spec names exactly. Pure and synchronous — it records state and rejects a transition that does not make sense from the current one (`HueEntertainmentStateMachineTests` covers both the happy path and every rejected transition); `HueEntertainmentService`'s own pump loop is the only thing that ever calls it, and owns all the actual network/timer/task work the machine itself deliberately knows nothing about.

**Pausing never disconnects.** `PlaybackPaused`/`PlaybackResumed` move directly between `Streaming` and `Paused` with no `Connecting` step in between — the DTLS session and the last colours sent stay exactly where they were, per the operator's explicit "the Entertainment session stays valid" requirement. `HueEntertainmentService.SendFrameOrKeepAliveAsync` resends the last built packet on a 1 s interval while paused (or while a `Streaming` tick finds no new frame yet) rather than 25 times a second, so the connection is kept alive without flooding the bridge.

**Distinguishing the four failure kinds the operator's spec names** (temporarily unreachable, revoked credentials, a vanished entertainment configuration, lost stream ownership to another application) is a `HueEntertainmentIssue` carried alongside the state, surfaced to the settings page via `HueStatus`/`GET RealtimeAmbilight/Hue/Status`. **Simplified for this round, and named as a simplification rather than left silent:** `StreamOwnershipLost` and `TemporarilyUnreachable` both currently route through the same `Recovering`/backoff machinery (bounded exponential backoff, 2 s to 60 s, ±20% jitter, capped consecutive-failure counting) rather than a specialised takeover-priority retry policy; the operator's spec's own priority/takeover requirement is satisfied at the *connect* level (this plugin's own `SetStreamingAsync` call always attempts to claim the stream, per the operator's stated authorisation to take over once the bound TV plays) but a dedicated, faster-cadence retry specifically for "another app is currently streaming" was not built as a separate path this round.

**Bridge health beyond "the UDP send did not throw":** not verified this round. The operator's spec explicitly warns that a successful send proves nothing about whether the lights are actually responding; this plugin currently has no independent health signal (e.g. reading the bridge's own reported streaming status) beyond send success/failure and the state machine's own issue tracking. Worth adding once the connect/reconnect path itself has been exercised against real hardware.

## Decision 7 — End-of-session behaviour and snapshotting

Two behaviours, exactly as specified: warm-white-dim (2700 K, 15% brightness, this project's own documented design default) or restore-previous-state. `HueSessionSnapshot` (`Core/Hue/HueLightSnapshot.cs`) is captured once per **playback session id** (`HueEntertainmentService` compares `_snapshot?.PlaybackSessionId` against the coordinator's own session id before capturing, so a mid-session reconnect never overwrites the snapshot with an already-synchronised, mid-stream light state) and cleared once consumed by the end-of-session PUT — an old snapshot can never outlive the session it was taken for, and a stale end-of-session command from an abandoned reconnect attempt cannot fire against a session that has since ended and been replaced, since `StopAsync`/`ApplyEndBehaviourAsync` only ever run from the state machine's own `Stopping` transition, itself only reachable once `_coordinator.ActiveSessionId` has actually gone `null` for the *current* tracked session.

**Recorded per light:** on/off, brightness percentage, and whichever single colour representation (`xy` or colour-temperature mirek) the bridge reported as the active `color_mode` — read via plain CLIP v2 `GET`/`PUT /clip/v2/resource/light/{id}` calls (`HueLightControl.cs`), not through the Entertainment DTLS path. **Not promised, per the operator's own explicit caveat:** a dynamic scene or effect running before the session cannot be reconstructed from a single static snapshot and is not attempted.

## Decision 8 — Settings page

A fifth tab ("Hue") alongside TV/WLED/Ambilight/Advanced, following the operator's numbered flow (scan → pair with press-link polling → pick an existing entertainment configuration → confirm the shared TV binding already set on the WLED tab, since a *second* device binding is explicitly out of scope → brightness/end-behaviour → save → status). **Deliberately less polished than the WLED wizard's**, consistent with "version 1" framing: no live LED preview during setup, a single flat panel rather than a multi-step guided flow. `HueController` (`Api/HueController.cs`) exposes the discovery/pairing/selection/status/unlink endpoints, all `[Authorize(Policy = "RequiresElevation")]`, matching every other admin surface in this plugin; nothing here is anonymous, unlike the WLED calibration wizard's TV-facing pages, since Hue setup has no TV-side component at all.

## Consequences

**Positive**

- WLED's own behaviour is unchanged; every existing test still passes (148/148 after this round, 51 of them new). The one shared production change (`FanOutFrameBuffer`) is a pure type substitution at three call sites plus one new class, and is itself covered by the existing `PlaybackEventCoordinatorTests`/`FrameSchedulingTests` continuing to pass unmodified.
- No bundled DTLS/crypto implementation; the one meaningfully-sized new runtime dependency (`Portable.BouncyCastle`, ~3.3 MB, the bulk of the ~8 MB total the packaged zip grew by) is a widely used, independently maintained library wrapped by a maintained higher-level client, not something this plugin owns.
- Every piece of pure logic (packetizer, config parser, spatial mapping, natural-light filter, state machine) is Core-layer and unit-tested without a live bridge, a DTLS stack, or a running Jellyfin host.

**Negative / accepted risk**

- The DTLS handshake's own lack of cancellability (Decision 1) and `StreamingHueClient`'s uncustomizable internal REST client are real, disclosed limitations of the adopted library, not fully closed this round.
- The spatial-mapping axis convention (Decision 3) is unverified against the primary reference and against real bridge data.
- `StreamOwnershipLost` recovery is not a dedicated fast-path (Decision 6).
- Packaging now ships four extra DLLs and the release archive is roughly 2.5× its previous size; `build/package.sh` was changed from `dotnet build`-then-copy to `dotnet publish` specifically because the old approach silently omitted every transitive package dependency (verified by inspecting `bin/` directly — it does not copy them), which would have shipped a plugin that installs, loads, and only fails the first time Hue is actually used, indistinguishable at a glance from the stale-Core-DLL defect this project has already been burned by once.

## Alternatives considered

| Alternative | Why rejected |
|---|---|
| Hand-rolled DTLS-PSK client | The operator's own decision rule: never implement crypto/DTLS from scratch when a maintained library exists. `Portable.BouncyCastle` underneath `HueApi.Entertainment` already does this correctly. |
| Reuse `StreamingGroup`/`EntertainmentLayer`'s built-in effects/dirty-tracking state for sending frames | Couples this plugin's own already-computed, already-filtered colours to a stateful dirty-comparison and layering system built for scripted programmatic effects, whose exact behaviour this session could not verify without a live bridge. A small, independently testable packetizer (Decision 1) gives full control and full test coverage instead. |
| Share `AmbilightFrameProcessor`'s internal `BlackBorderDetector`/sampling state with Hue | Requires refactoring already-working, already-tested WLED code purely to serve a brand-new, unvalidated feature — exactly the risk this integration is required not to take. A second, independent, cheap detector instance costs little and touches nothing WLED depends on. |
| Fold Hue into `JellyfinWledOutputService`'s existing pump loop | Would make a Hue reconnect/backoff able to stall WLED output by sharing a loop, a lock, or a buffer — the one thing the operator's spec explicitly forbids. A fully separate hosted service with its own loop, its own `FanOutFrameBuffer` subscription, and its own try/catch boundary structurally cannot do that. |
| Company `HueApi.Entertainment`'s `AutoUpdateAsync` for the send loop | Runs its own `Task.Run` + `Thread.Sleep` busy loop with its own timing model, a second, different concurrency pattern alongside this project's existing PeriodicTimer-based pump loops (`JellyfinWledOutputService.RunPumpAsync`). Calling `ManualUpdate`/`Send` from this project's own pump loop keeps one consistent pattern and full control over cadence and cancellation. |

## Not yet done / explicitly deferred

- Live pairing, streaming, and everything that requires it (see the hardware checklist in `docs/handoff/CURRENT.md`).
- Closing the `SetStreamingAsync` certificate-validation gap (Decision 1) by reimplementing `ConnectAsync`'s REST call against this plugin's own pinned client.
- A dedicated fast-path retry for lost stream ownership specifically (Decision 6).
- Independent bridge-side health verification beyond send success (Decision 6).
